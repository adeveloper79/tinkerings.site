### The USB-C Quick-Pull Power Glitch
While testing power supplies, I discovered a bizarre physical quirk:
- Cold boot from power strip: **Black screen.**
- **Quickly yank out the USB-C power plug and slam it back in within a second: The faint image appeared reliably every single time.**

This was the smoking gun. It proved that **the issue was a power-on reset and timing synchronization bug**:
When power was rapidly cycled, the RTD2660's bulk filter capacitors held enough charge to keep the 8051 registers alive while the panel's internal analog charge pumps underwent a full hard reset, allowing the subsequent SPI initialization commands to land in the panel's active reset window.

My ESP32 sniffer claimed commands were being sent on cold boot, so why was the panel ignoring them?

## 8. The Breakthrough: Raspberry Pi Pico & Microsecond PulseView

The ESP32-C3 sniffer, while great for logging bytes, lacked analog waveform fidelity and microsecond timing accuracy.

I remembered I had a box of spare **Raspberry Pi Pico** boards sitting in a 3D-printed case. 

![3D-printed doggy](assets/3dprintedoggy_extra.jpg)

I recalled an open-source project by Gusman:
🔗 **[gusmanb/logicanalyzer](https://github.com/gusmanb/logicanalyzer)** a firmware that turns the RP2040 into a 100 MHz, 24-channel logic analyzer compatible with Sigrok and PulseView.

![Raspberry Pi Pico wired as a high-speed logic analyzer to the RTD2660 pins](assets/pico_logicanalyzer.jpg)

I soldered fine enameled wires directly from the RTD2660's pins to the Pico's GPIO headers, opened PulseView on my PC, and captured the boot sequence of the **original factory firmware** versus my **custom firmware**.

When the waveforms rendered on my monitor, the issue was immediately clear:
**The timing was WAAAY off.**

Here is the capture of the working original factory firmware:

![Logic analyzer waveform capture of the working factory initialization](assets/working_logicanalyzer.png)

And here is the capture of my custom firmware that produced only the faint display:

![Logic analyzer waveform capture of the faint initialization showing timing mismatch](assets/faint_init_logicanalyzer.png)

![Logic analyzer waveform capture during the warm-plug power glitch](assets/warm_plugging_faint_logicanalyzer.png)

The differences were critical:
1. **Reset Recovery Delay**: The ST7701 datasheet specifies a minimum reset low pulse of 10ms, but critically requires **at least 120ms of idle stabilization time AFTER RST goes high** before sending SPI commands. My custom code was blasting commands barely 2ms after reset, before the panel's internal oscillator had even stabilized!
2. **CS (Chip Select) Framing**: The factory firmware held **CS LOW across an entire multi-byte register packet**. My code was toggling CS high and low between every single byte, which continuously reset the ST7701's internal SPI byte-counter!
3. **Clock Symmetry**: My software bitbang delays relied on uncalibrated `_nop_()` loops that ran with severe jitter, violating the ST7701's minimum data setup and hold times.

Completely rewrote the 9-bit SPI bitbang driver:

```c
// Calibrated 9-Bit SPI Bitbang Driver for ST7701
void ST7701_Write(BYTE bIsData, BYTE ucValue)
{
    BYTE i;
    
    ST7701_SCL = 0;
    
    // 9th bit: 0 = Command, 1 = Parameter/Data
    ST7701_SDA = bIsData ? 1 : 0;
    ST7701_SPI_DELAY();
    ST7701_SCL = 1;
    ST7701_SPI_DELAY();
    
    // 8 Data Bits (MSB First)
    for(i = 0; i < 8; i++)
    {
        ST7701_SCL = 0;
        ST7701_SDA = (ucValue & 0x80) ? 1 : 0;
        ST7701_SPI_DELAY();
        ST7701_SCL = 1;
        ST7701_SPI_DELAY();
        ucValue <<= 1;
    }
    
    ST7701_SCL = 0;
}
```

I compiled, flashed, and powered on cold.
**The panel fired up with image output on cold boot!**

## 10. Cracking the Binary: 249 Commands and the PinShare Riddle

With the display firing, I needed the exact internal register values that the factory firmware was using to eliminate all remaining flicker and color artifacts.

AI wrote Python disassemblers to tear apart the `live_dump.bin`.

### Milestone 1: The 249-Command Table at `0x6B31`
Tracing calls from the main hardware init function (`0x0C8DC`), I found an 8051 routine loading `DPTR` with `#0x6B31`. 
Decompressing that table revealed the manufacturer's exact **249 ST7701 initialization commands**:
- **Book Selection Registers (`0xFF`)**: Navigating into Command2 Book 0, Book 1, and Book 2.
- **Charge Pump Timings (`0x11`, `0xCD`, `0xCC`)**: Powering internal gate voltages.
- **Analog Gamma Curves (`0xE0`, `0xE1`)**: 16-point voltage step curves for color linearity.

### Milestone 2: The PinShare Riddle at `0x0CF44`
This was one of the most critical structural discoveries. The RTD2660 uses internal multiplexers called **PinShare registers** (`0xFF96` through `0xFFA4`) that configure whether pins function as ADC inputs, PWM channels, or push-pull GPIOs.

At offset `0x0CF44` in the factory ROM, I found this table:
```c
MCU_PIN_SHARE_CTRL02_FF98 = 0xA3; // Pin 52 -> P6.2 Push-Pull (SCL)
MCU_PIN_SHARE_CTRL03_FF99 = 0x89; // Pin 53 -> P6.3 Push-Pull (CS)
MCU_PIN_SHARE_CTRL04_FF9A = 0x46; // Pin 55 -> P6.5 Push-Pull (RST)
MCU_PIN_SHARE_CTRL06_FF9C = 0xA4; // Pin 54 -> P6.4 Push-Pull (SDA)
```
In our open-source codebase, these registers were never being initialized! Pins 52–55 were floating as high-impedance inputs with weak pull-ups, which explained the distorted analog signal levels on the SPI bus.

### Milestone 3: The DDC/CI Interrupt Collision at `0x12C8`
When I tried controlling the monitor via VESA DDC/CI commands using `ddcutil` on Linux, the command would hang with `I2C bus timeout`.

Disassembling the factory ISR at `0x12C8` revealed why:
```assembly
MOV     A, 0xFF27           ; Read MCU_I2C_STATUS_FF27
MOV     R7, A
ANL     A, #0x04            ; Test DINI (Data In Interrupt)
JZ      CHECK_DOUT
; ... Process Incoming Host Byte ...
SJMP    EXIT_ISR

CHECK_DOUT:
MOV     A, R7
ANL     A, #0x08            ; Test DOUTI (Data Out Interrupt)
JZ      EXIT_ISR
; ... Transmit Outgoing Byte to Host ...
EXIT_ISR:
RETI
```
The open-source firmware was using two independent `if` statements:
```c
if (MCU_I2C_STATUS_FF27 & _BIT2) { /* RX */ }
if (MCU_I2C_STATUS_FF27 & _BIT3) { /* TX */ }
```
During an I2C repeated-START condition, both bits could be high simultaneously. The open-source code executed both blocks, corrupting the transmit buffer pointer. Changing it to an `if / else if` mutual exclusion fixed `ddcutil` instantly.

![VESA DDC/CI software controls working over HDMI with ddcutil](assets/DDC.jpg)

### Milestone 4: Unlocking Hardware ISP Flashing Over HDMI
Digging through the memory map around `0xFF60`–`0xFF70`, I found Realtek's built-in **hardware In-System Programming (ISP) engine**:
- It listens on I2C 7-bit slave address **`0x4A`** directly over the HDMI DDC lines.
- Writing `0x80` to register `0x6F` halts the 8051 processor and maps the SPI flash controller straight to I2C!
- This discovery eliminated the need to disassemble the enclosure or use the CH341A programmer, allowing full 256 KB firmware updates to be flashed directly over HDMI via a Raspberry Pi in ~30 seconds using `python3 rtd266x_flash.py`.

## 11. The Polish: True 60.00 Hz, Dark-Mode OSD, and Audio Stripping

With the display running and software controls operational, I focused on final polish:

### 1. Eliminating Micro-Stutter: Exact 60.00 Hz DPLL Math
The factory firmware drove the panel at an odd 56.11 Hz (33.90 MHz pixel clock), causing frame judder on standard 60 Hz HDMI video.
Using the panel's active geometry ($672 \times 899$), I recalculated the DPLL frequency synthesizer:
$$f_{\text{pixel}} = 672 \times 899 \times 60.00\text{ Hz} = 36,247,680\text{ Hz} \approx \mathbf{36.25\text{ MHz}}$$
I updated the EDID DTD1 descriptor and recomputed the checksum. The panel locked to an exact **60.0038 Hz** refresh rate. Smooth as butter.

### 2. Sleek Dark-Mode OSD Redesign
The factory 1990s-era yellow-and-blue blocky OSD was completely replaced. I designed a modern dark-mode interface:
- Deep OLED Slate background (`#12161F`).
- Subtle 1px border (`#26334D`).
- Electric Cyan accent slider (`#38BDF8`) paired with a pure white percentage readout (`#FFFFFF`).
- Shifted title strings to Row 1 for balanced vertical symmetry.

![The redesigned sleek dark-mode OSD running on the panel](assets/OSD.jpg)

### 3. Pure Video EDID: Stop Stealing My Audio!
Because the EYA board has no audio amplifier or speakers populated, connecting it to a PC or handheld caused the operating system to detect the HDMI audio descriptor and silence the computer's internal speakers.
- Created `#define _HDMI_AUDIO_SUPPORT _OFF`.
- Stripped the CEA-861 Audio Data Block and Speaker Allocation Block.
- Cleared the Basic Audio bit in Header Byte 3 (`0x71` $\to$ `0x31`) and recomputed the checksum (`0x8C`).
- Host PCs now detect the display strictly as a video-only sink, keeping audio output on internal speakers.

### 4. Full 60.00 FPS Native Perfection
With the DPLL set to 36.25 MHz, the ST7701 running full 24-bit RGB with correct R-B swapping, calibrated active margins, and the modern dark-mode OSD in place:

## 12. Retrospective & Takeaways

What started as a simple screen purchase turned into an end-to-end masterclass in hardware hacking, 8051 assembly disassembly, signal integrity, and embedded C firmware design.

A few key lessons from the bench:
1. **Never trust that a replacement panel is a drop-in replacement.** Check the pinout datasheet if exists first.
2. **When vendor documentation is non-existent, build your own instruments.** An ESP32 or a $4 Raspberry Pi Pico running `gusmanb/logicanalyzer` can reveal microsecond timing bugs that software logging will never catch.
3. **Power cycle quirks are always timing clues.** If a board only boots when you rapidly replug power, you have a reset recovery or clock stabilization issue.
4. **Visual tools beat blind trial-and-error.** Building the [web emulator](https://adeveloper79.github.io/rtd2660-emu/) turned a wall of hex registers into an understandable state machine.
